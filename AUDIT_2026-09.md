## CRITICAL

### C1. Any signed-in customer can make themselves an admin
**What.** A logged-in customer can run, from the browser with the ordinary anon
client, `update profiles set role='admin' where id=<their own id>` and it
succeeds. `is_admin()` then returns true, unlocking the entire admin panel and
every `is_admin()`/`is_staff()` RLS policy (read all orders, all customers, all
addresses; write catalog, coupons, settings). The same UPDATE also lets them set
`cod_trust_level='vip'`, zero `no_show_count`, and clear `blocked_at`, defeating
the COD abuse controls.

**Evidence.** Run as customer `56dfcf10…` (JWT-simulated, rolled back):
```
update public.profiles set role='admin' where id='56dfcf10…';
select public.is_admin();   -- => true
```
The migration `20260617000005_rls.sql` does `REVOKE UPDATE (role) ON profiles
FROM authenticated`, but production shows `authenticated` **still holds** table-
level `UPDATE` on `profiles` (and column `UPDATE` on `role`). A later blanket
`GRANT` (the Supabase default `GRANT ALL ... TO authenticated`, or a reset) re-
granted the column and silently nullified the revoke. `information_schema`:
```
role_table_grants: authenticated | UPDATE   (present)
column_privileges: authenticated | role | UPDATE   (present)
```
`profiles_update_own` RLS allows updating one's own row with no column
restriction, so the write is permitted.

**Why it matters.** Complete authorization bypass reachable by anyone who can
register. This is the single most severe issue in the system.

**Fix (needs a production DB change — do NOT deploy without your go-ahead).**
Re-revoking columns is fragile because any future `GRANT ALL` re-breaks it. Use a
BEFORE-UPDATE trigger as the durable guard, plus the revoke:
```sql
-- 1. Immediate: re-revoke the sensitive columns.
REVOKE UPDATE (role, cod_trust_level, no_show_count, blocked_at, blocked_reason)
  ON public.profiles FROM anon, authenticated;

-- 2. Durable: reject privilege-column changes from non-admins even if a future
--    grant re-opens them.
CREATE OR REPLACE FUNCTION public.guard_profile_privilege_columns()
RETURNS trigger LANGUAGE plpgsql SECURITY DEFINER SET search_path=public AS $$
BEGIN
  IF public.is_admin() THEN RETURN NEW; END IF;
  IF NEW.role            IS DISTINCT FROM OLD.role
  OR NEW.cod_trust_level IS DISTINCT FROM OLD.cod_trust_level
  OR NEW.no_show_count   IS DISTINCT FROM OLD.no_show_count
  OR NEW.blocked_at      IS DISTINCT FROM OLD.blocked_at
  OR NEW.blocked_reason  IS DISTINCT FROM OLD.blocked_reason THEN
    RAISE EXCEPTION 'cannot modify privileged profile columns' USING ERRCODE='42501';
  END IF;
  RETURN NEW;
END $$;
DROP TRIGGER IF EXISTS profiles_guard_privilege ON public.profiles;
CREATE TRIGGER profiles_guard_privilege BEFORE UPDATE ON public.profiles
  FOR EACH ROW EXECUTE FUNCTION public.guard_profile_privilege_columns();
```
Effort: ~30 min including a re-test with the same JWT simulation. I have the test
ready and can apply + verify on your approval.

## HIGH

### H1. Admin Settings and Coupons pages cannot save anything
Every write on these screens targets a table where `anon`/`authenticated` have no
INSERT/UPDATE/DELETE grant (`store_settings`, `tax_rates`, `coupons`,
`delivery_zones`, `delivery_methods` are all REVOKEd; only an RLS "admin_write"
policy exists, which cannot override a missing table grant). So:
- **Coupons** (`admin/coupons/page.tsx`): create/edit/archive/delete all fail with
  `permission denied`. The "New coupon" button is a dead end. (There are 0 coupons
  in production, consistent with this never having worked.)
- **Settings** (`admin/settings/page.tsx`): both Save buttons can never succeed;
  the General tab has no save path at all and `store_settings` is never read or
  written anywhere in admin — `brand_name`, `cod_only`, `support_email`,
  `review.auto_publish`, delivery cities, etc. are all uneditable from the UI.

**Fix.** Route these writes through `SECURITY DEFINER` admin RPCs (like the order/
review/user RPCs already do), or grant the admin role table privileges. ~1 day.

### H2. Admin Customers page is blank (queries a dropped column)
`admin/customers/page.tsx` selects `total_amount` from `orders`; that column only
existed on the dropped legacy table (current schema has `total_minor`). PostgREST
returns 42703, the code ignores the error, and the page renders empty with no
message. Even if it loaded, spend would always show 0. **Fix:** select
`total_minor`, sum with `sumMinor`, format with `formatPkr`. ~1 hr.

### H3. Production is missing almost every environment variable
Production has exactly 3 vars (`NEXT_PUBLIC_SITE_URL`, `NEXT_PUBLIC_SUPABASE_URL`,
`NEXT_PUBLIC_SUPABASE_ANON_KEY`); `.env.example` documents ~15. Most consequential:
`SUPABASE_SERVICE_ROLE_KEY` is absent, so the notification processor (and any
future service-role work) 500s — the live endpoint literally returns
`"SUPABASE_SERVICE_ROLE_KEY is not set"`. Also absent: all `GOOGLE_SMTP_*`,
`NOTIFICATIONS_PROCESS_SECRET`, `NEXT_PUBLIC_GOOGLE_SITE_VERIFICATION`. **Fix:**
set the server-side vars on Vercel Production (see Email section). ~30 min.

### H4. Staff role is admitted to the admin shell but most of it is admin-only
`admin/layout.tsx` lets `role in (admin, staff)` in, but catalog/products/
categories writes and the user-management RPCs are all `is_admin()`-gated. A staff
login sees the full nav, then hits raw RLS errors on Products/Catalog and "could
not load users" on Staff. Worse, storage insert is `is_staff()`: a staff image
upload succeeds and the subsequent product insert fails, leaving an orphaned file.
**Fix:** either gate the nav/pages to the role that can actually use them, or lift
the relevant policies to `is_staff()` deliberately. ~half day.

### H5. Legal pages are missing; storing PK customer addresses without a privacy policy
`/terms`, `/privacy`, `/privacy-policy`, `/cookies` all return 404. The footer
prints "Terms & Conditions | Cookies | Privacy Policy" as plain text (not even
links). The site collects names, phone numbers and delivery addresses. Pakistan's
draft PDPB and ordinary consumer-protection expectations make a privacy policy and
terms the norm for taking orders and storing addresses; their absence is a
compliance and trust gap, and thin/placeholder legal pages also hurt SEO trust
signals. **Fix:** add real Terms, Privacy, and a returns/refund policy; link them
from the footer. ~half day of content + routes.

### H6. Homepage has no `<h1>`
The live homepage renders zero `<h1>` elements (verified in the served HTML);
"Welcome to KAKEEZ Bakeshop" and "Shop Best Sellers" are both `<h2>`. The most
important page for the brand term has no top-level heading. **Fix:** promote the
welcome heading (or a visually-hidden brand H1) to `<h1>`. ~15 min.

## MEDIUM

### M1. Invalid product/category URLs return HTTP 200 (soft 404)
`/product/does-not-exist` and `/category/does-not-exist` return **200** with a
`noindex` tag rather than a 404 (streamed `notFound()` returns 200). Google treats
200+noindex inconsistently and it wastes crawl budget. **Fix:** ensure these
resolve as true 404s (a route-level `not-found.tsx` and/or non-streamed handling).
~1–2 hr.

### M2. Footer newsletter box is fake
The "Stay in the Loop / Your e-mail" box in `Footer.tsx` is a styled `<div>` with
a decorative arrow — no input, no submit, no handler. It looks interactive and
does nothing. **Fix:** wire it to a real list (or remove it). ~1–3 hr depending on
provider.

### M3. "Karachi" is hard-coded across a Lahore business
Default city is `"Karachi"` in checkout (`city: "Karachi"` sent to both preview and
`create_order`), the account address form default, and the signup popup's address
insert; the sole `delivery_zones` row is Karachi. Blast radius: it is **written
into `delivery_address_snapshot`** — both live orders show `"city":"Karachi"` even
though KKZ-000002's line1 is a Johar Town, Lahore address. Delivery fee is a flat
Rs 99 regardless (only one active method), so it is a data-quality/label bug, not a
mispricing one, but it corrupts the city on every order. **Fix:** change the
defaults to Lahore and the delivery zone to Lahore; leave historical snapshots
alone. ~1 hr (defaults) + a decision on the zone.

### M4. No analytics and no error tracking
No GA/Plausible/PostHog and no Sentry/error reporting anywhere in the codebase.
Production failures are invisible and you have no traffic/conversion data. **Fix:**
add lightweight analytics (Vercel Analytics or Plausible) and Sentry (or Vercel's
error monitoring). ~2–4 hr.

### M5. Admin dashboard: wrong status labels and float revenue
`admin/page.tsx` colours rows by `status === 'baking'`/`'pending'` — neither is in
the status enum, so every real status except `cancelled` renders green. The revenue
KPI sums rupee floats (`reduce(acc + total_minor/100)`) and counts cancelled/
unpaid/failed orders as revenue. **Fix:** use the real enum and sum in paisa with
`sumMinor`/`formatPkr`, excluding non-revenue statuses. ~2 hr.

### M6. Product delete is a hard delete; image pipeline has no guards
Admin product delete issues a real `DELETE` even though the schema has
`deleted_at` soft-delete (which the public read policy already respects). Image
upload enforces size/type in the browser only — the `products` bucket has **no
file-size or MIME limit** and no dimension check or compression, so the 2000×2000
~2.9 MB PNGs are accepted as-is. Uploads happen before save, so cancelling orphans
the object. Production already has **57 orphaned objects (152 MB)** in the bucket
not referenced by any `product_images` row. **Fix:** soft-delete; add bucket
`file_size_limit`/`allowed_mime_types`; upload on save; sweep orphans. ~half day.

### M7. Cart badge hydration pattern (the known bug)
`Navbar.tsx` reads `useCart(state => state.totalItems())` during render from a
localStorage-persisted store. Server renders no badge; a client with a non-empty
cart renders one — a hydration mismatch. (In the prod build React reconciles it
rather than throwing visibly, and zustand v5's async rehydration masks it in some
paths, but the pattern is still incorrect and can flash/mismatch.) eslint here
enforces `react-hooks/set-state-in-effect`, so the naive mounted-flag fix is
rejected. **Fix:** gate on hydration with `useState`+`useEffect` guarded by the
lint rule, or read the count via `useSyncExternalStore`/a `useCart.persist`
`onFinishHydration` flag so the first client render matches the server. ~1–2 hr.

### M8. No rate limiting / abuse controls on public actions
Nothing throttles review submission, coupon validation (`validate_coupon_for_cart`
returns validity to any authenticated caller — brute-forcable), or account
creation beyond Supabase's auth limits. The COD abuse settings exist in
`store_settings` but nothing reads/enforces them. **Fix:** add per-user/IP limits
(edge middleware or a DB counter) and wire the COD caps into `create_order`. ~1 day.

### M9. Search is effectively name-only
Navbar search ORs `name` and `short_description`, but **all 31 products have an
empty `short_description`**, so only names are searched. No fuzzy/typo tolerance
despite `pg_trgm` being installed (and an index `idx_products_name_trgm` exists but
the query uses `ilike`, not trigram similarity). **Fix:** include `description`,
and use trigram similarity for typo tolerance. ~2–4 hr.

### M10. Migration ↔ production drift
Beyond C1 (the ineffective column REVOKE), the repo's `create_storage` migration
defines permissive storage policies that don't match the tighter live ones, and
`20260615000001_seed_admin.sql` still contains `crypt('admin')` for
`admin@kakeez.com` — a fresh `supabase db reset` would recreate a known-credential
admin (the live DB no longer has that user; the risk is environment recreation).
**Fix:** reconcile migrations to the live schema (`supabase db diff`) and delete/
neutralise the seed-admin credential. ~half day.

## The email chain (MUST-FIX) — what I did and what remains

**Root cause, confirmed in prod.** The DB trigger enqueues correctly (9 rows sit
in `public.notifications`, all `status='queued'`, none ever `sent`). Nothing
invoked the consumer at `src/app/api/notifications/process/route.ts`: there was no
`vercel.json` and thus no cron; production lacked `NOTIFICATIONS_PROCESS_SECRET`
(so the endpoint would reject a call) and every `GOOGLE_SMTP_*` var (so it could
not send). `NOTIFICATIONS_DRY_RUN` defaults to **on** when unset (`!== 'false'`),
so even a successful call would only log. On top of that there is **no custom
SMTP**, which is why signup confirmation is disabled (`enable_confirmations=false`)
and password reset silently does nothing for real customers — Supabase's built-in
mailer only delivers to project team members.

**Mechanism chosen: Vercel Cron.** Committed on branch
`fix/notification-email-delivery`:
- `vercel.json` runs `/api/notifications/process` every 2 minutes.
- `route.ts` now has a **GET** handler (Vercel Cron issues GET; the route was
  POST-only, so the cron would have 405'd), accepts either
  `NOTIFICATIONS_PROCESS_SECRET` or Vercel's auto-injected `CRON_SECRET`, and
  **fails closed** when no secret is set (previously an unset secret would have
  left the endpoint open once a service key existed). Pinned to the Node runtime.

Rationale vs alternatives: a **direct call at order creation** would put an SMTP
round-trip (and its failure modes) on the checkout path — the queue exists
precisely to avoid that. A **Supabase Edge Function + pg_cron** is viable
(`pg_cron`/`pg_net` are available but not installed) and is the right fallback if
you're on Vercel **Hobby**, where cron is limited to once/day; Vercel **Pro** runs
the 2-minute schedule. Vercel Cron reuses the existing, working consumer with the
least new surface, so it's the primary recommendation.

**Proven.** The send path was tested end to end with **zero external credentials**:
a throwaway in-process SMTP server + the project's real `nodemailer`, rendering the
three live templates from the actual queued payloads. All three delivered with
correct recipients, subjects and bodies, and correct money (`462900` → `Rs.
4,629.00`): the customer "order received", the admin "new order" alert, and the
"status changed to cancelled" note. Typecheck and lint pass on the changed route.

**What only you can finish (owner-only secrets + production release).** I did not
set production secrets, deploy, drain the backlog, or email real customers — each
needs a credential I shouldn't hold or an action on real people that needs your
say-so:
1. Set on Vercel **Production**: `SUPABASE_SERVICE_ROLE_KEY` (retrievable via the
   authenticated `supabase` CLI), `NOTIFICATIONS_PROCESS_SECRET` **and** matching
   `CRON_SECRET` (a long random string), `GOOGLE_SMTP_HOST/PORT/SECURE/USER/PASS/
   FROM`, `KAKEEZ_ADMIN_EMAIL`, and `NOTIFICATIONS_DRY_RUN=false`.
2. Enable Supabase custom SMTP and turn the branded auth templates back on:
   uncomment `[auth.email.smtp]` and the six templates in `supabase/config.toml`,
   set `enable_confirmations=true`, then `supabase config push`.
3. Merge the branch and deploy.
4. **Backlog decision:** don't drain in dry-run — it would mark the 9 rows `sent`
   without sending and destroy the record that they're pending. Drain only after
   real SMTP is live. The 2 customer confirmations are for a cancelled order (Jun)
   and KKZ-000002 (Aug 30); consider emailing KKZ-000002's customer manually given
   the 8-day delay.

DNS is ready for this: `kakeez.com` has GoDaddy MX, an SPF record
(`v=spf1 include:secureserver.net -all`) and DMARC (`p=quarantine`). Sending from
a Gmail/Workspace SMTP `From: orders@kakeez.com` will need that sender aligned with
SPF/DKIM to avoid the quarantine policy — worth checking deliverability.

worth it so you can recover to a point in time rather than a daily snapshot.
